# PotatoCode Spec 驱动开发

把需求逐步整理为四份相互对应的文档，再按文档实现和验收：

```text
spec.md（做什么）→ plan.md（怎么做）→ task.md（怎么执行）→ checklist.md（如何验收）
```

## 使用范围

在以下任务中使用本 skill：

- 新章节或新功能；
- 新模块或跨模块改动；
- 架构、公共接口、配置格式或用户可见行为发生明显变化。

以下任务直接修改并按影响范围验证：

- 局部且边界明确的缺陷修复；
- 文案、注释或格式调整；
- 不改变行为的机械重构；
- 用户明确要求跳过文档流程的任务。

## 开始前

1. 阅读当前代码、README 和相关章节文档。
2. 查看最近章节的 `spec.md`、`plan.md`、`task.md`、`checklist.md`，沿用项目格式。
3. 明确本次工作的目标、边界和可观测的完成标准。只有会实质改变方案的缺失信息才询问用户。

## 阶段一：spec.md

说明背景、目标、功能需求、非功能需求、不做的事和验收标准。

- 描述系统行为，避免提前绑定文件、类名和方法名。
- 每条功能需求至少对应一条验收标准。
- 消除 `TODO`、`TBD`、互相矛盾或可作多种解释的表述。
- 文档完整后请用户审批；有修改意见时更新后重新提交。

## 阶段二：plan.md

基于已批准的 spec 说明架构、组件职责、核心接口、数据结构、模块交互、
文件组织和关键技术决策。

- 说明每条功能需求由哪个组件负责。
- 写清依赖关系和重要取舍。
- 设计必须保持在 spec 确定的范围内。
- 文档完整后请用户审批。

## 阶段三：task.md

基于已批准的 spec 和 plan，列出要创建、修改和测试的文件，并拆成有序任务。

- 每项任务写明依赖、具体步骤和验证命令及预期结果。
- 任务应聚焦且可以独立判断是否完成。
- 明确串行和可并行部分，避免循环依赖。
- 文档完整后请用户审批。

## 阶段四：checklist.md

基于已批准的前三份文档设计可执行验收项。

- 覆盖 spec 中的每条验收标准。
- 包含集成检查、Ruff、pytest，以及适用时的 mypy。
- 至少包含一个完整的用户可见端到端场景。
- 每项写成“执行什么、应观察到什么”，避免依赖内部实现细节。
- 文档完整后请用户审批。

## 实现与验收

四份文档均获批准后再编写实现代码。按 `task.md` 执行，每完成一个逻辑单元就运行对应验证；失败时先修复再继续。

实现完成后逐项执行 `checklist.md`，记录实际命令、结果和必要证据。若检查失败，修复并重新执行。最终报告通过项、仍未通过项及端到端结果，不用推测代替执行证据。

## 核心约束

- 用户最新的明确要求优先于既有文档；范围变化时同步更新受影响的文档。
- 保持 spec、plan、task 和 checklist 之间可追溯且无矛盾。
- 只实现已批准范围内的内容。
- 先取得运行或观察证据，再报告完成。
