# 工具遍历范围修订 Spec

> 本章为**修订章**：它不新增能力，而是修订 ch03「工具系统」中 F2-按模式找文件 / F2-搜代码内容两个工具
> 的遍历范围与扫描效率，改动对应的验收标准是 ch03 的 AC6。ch03 的四份文档保持原样，作为该章交付时的历史记录。

## 背景

ch03 交付了六个核心工具，其中「按模式找文件」与「搜代码内容」以项目根为起点**全量递归遍历**——凡是项目根目录下的文件，不问来源、不问价值，一律进入遍历与匹配。

在本仓库实测，这个"全量"的构成极不均衡：

| 范围 | .py 文件数 | 行数 |
|---|---|---|
| 项目自身（src / tests / docs / examples） | 86 | 12,670 |
| `.venv`（虚拟环境） | 5,196 | 1,135,991 |
| **.venv 占比** | **98.4%** | **98.9%** |

也就是说，默认遍历的语料里 98.9% 是第三方依赖，项目自身只占 1.1%。由此产生两个可观测后果：

**其一，结果配额被噪声吃掉。** 两个工具都有 100 条命中上限，配额是"先到先得"。实测各模式返回结果中来自 `.venv` 的比例：

| 调用 | 返回条数 | 其中来自 `.venv` | 占比 |
|---|---|---|---|
| 按模式找文件 `**/*.md` | 55 | 19 | 34% |
| 按模式找文件 `**/*.py` | 100 | 14 | 14% |
| 按模式找文件 `**/*.json` | 21 | 19 | **90%** |
| 按模式找文件 `**/*.txt` | 65 | 64 | **98%** |
| 搜代码内容 `import asyncio`（限 `*.py`） | 95 | 73 | **76%** |

模型问"项目里有哪些 txt / json 配置"时，拿回的基本是第三方包内部文件，等于没回答。

**其二，搜代码内容工具存在一层可省的扫描开销。** 稳定复测一次全量搜代码内容耗时 **约 2.2 秒**——占 30 秒工具超时上限的 7%，**当前并未逼近超时**。但这 2.2 秒里有一层可以省掉：现有逐行扫描实现每切出一行都要重新扫描一遍剩余缓冲，吞吐只有朴素按行迭代的 **40%**。同一份 1,148,661 行语料对照实测：

| 扫描实现 | 耗时 | 扫描行数 | 命中数 |
|---|---|---|---|
| 现有逐行切分 | 2.01s / 2.21s | 1,148,661 | 95 |
| 朴素按行迭代 | 0.81s / 0.87s | 1,148,661 | 95 |

两者结果完全一致（行数、命中数逐条相同），差距纯粹是切分方式的常数开销。

> **测量更正**：本节早期版本写作"9.9s ~ 27.9s、已逼近工具级超时"，该读数来自本会话首次运行的污染测量（冷缓存 / 杀毒扫描首次遍历依赖目录），用原脚本稳定复测无法重现（复测值 2.13s / 2.21s）。据此更正：本问题的真实形态是**结果质量**（其一的配额侵占）与**可省的扫描开销**，**不是**超时风险。

已有的相关设施与本次改动的关系：ch06 的路径沙箱把文件类工具限制在项目根内，但它只约束"不能出去"，不解决"根目录**内部**哪些子目录不值得进"；ch08 的工具结果落盘处理的是"单条结果过大"，与"命中来源太杂"是两回事。本次补的是中间这一层：**遍历范围**。

## 目标

- 两个遍历类工具默认跳过不值得搜索的目录，把 100 条结果配额留给项目自身内容。
- 搜代码内容工具在默认范围内的耗时降到**秒级以下**；逐行扫描吞吐对齐朴素按行迭代，消除这层可省的开销（当前只有朴素迭代的 40%）。
- 保留"确实需要时能搜进去"的通路，不牺牲可达性——排除是默认行为，不是硬墙。
- 不破坏既有行为：参数形态、结果文本格式、错误语义、只读标记、权限链路一律不变。

## 功能需求

- F1: 默认排除的目录集合
  两个遍历类工具默认跳过两类目录，判定只看**目录名**，不看层级深浅、不做内容识别：
  - **隐藏目录**——名字以 `.` 开头的目录。这一条规则同时覆盖虚拟环境（`.venv`）、版本库元数据（`.git`）、各类工具缓存（`.mypy_cache` / `.pytest_cache` / `.ruff_cache`）与本项目自有的运行时目录（`.potatocode`）。
  - **固定噪声目录**——`__pycache__` 与 `node_modules` 两个非隐藏但公认无搜索价值的目录。

  被排除目录下的**任意深度**内容都不参与遍历与匹配。排除是**默认行为**而非不可绕过的限制：用户不可配置该名单（见「不做的事」），但可通过 F2 的通路搜进去。
  已知代价（接受）：`.github`、`.claude` 等同样以 `.` 开头，默认也不再被搜到——需要时走 F2。

- F2: 排除只作用于搜索根之下
  排除判定基于**相对于搜索根的路径**，而非绝对路径。判定对象是该路径中**除文件名以外的目录分量**：任一分量命中 F1 的规则即跳过。

  由此自然获得逃生口：当搜索根本身就是某个被排除目录时（如搜索根指向依赖包目录内），该目录名不在"根之下的相对分量"里，规则不生效，遍历正常进行。即**"默认不进去"与"显式要求进去"两种意图可区分**，无需新增参数。

- F3: 两个工具一致适用
  按模式找文件与搜代码内容共用同一套排除规则与同一条 F2 的作用域语义。搜代码内容工具原有的"按文件名过滤"参数与排除规则**叠加**生效（先过排除、再过文件名过滤），不互相覆盖。

- F4: 逐行扫描的效率与超长行语义
  搜代码内容的逐行扫描按块读取的行为保持不变，但**消除"每切一行重扫剩余缓冲"的开销**，使全量扫描吞吐对齐朴素按行迭代（目标：同语料下耗时不超过朴素迭代的 1.5 倍；实测改法为 1.0 倍）。

  同时**完整保留既有超长行语义**：单行超过阈值时只保留前缀、标记该行未完整搜索、不把整行读进内存。加速不得以放宽内存约束或改变"是否命中"的判定为代价——扫描出的行号序列与命中集合必须与改动前**逐条一致**。

## 非功能需求

- N1: 效率——在本仓库（1.14M 行语料）下，默认范围的全量搜代码内容耗时**低于 1 秒**；显式指定依赖目录为搜索根、搜全量语料时耗时**低于 5 秒**（改法实测 0.85s）。两者都远低于工具超时上限，留出充足余量。
- N2: 接口零变化——两个工具的名称、参数 Schema（属性、类型、必填项）、给模型看的描述、只读标记均不变；结果文本格式不变（按模式找文件为路径列表，搜代码内容为 `文件:行号:内容`，截断时追加截断标注）。工具定义的总数与顺序不变。
- N3: 不破坏 ch03——ch03 验收标准 AC6 在修订后**依然成立**（glob 模式能列出匹配文件；内容搜索能返回命中位置）；既有单测全部通过；无匹配、非法正则、单文件读失败跳过、结果截断等既有行为不变。
- N4: 不破坏 ch04~ch08——Agent Loop 编排、保序分批并发、只读工具的并发执行、权限沙箱判定、MCP 工具注册、上下文管理链路均不因本次改动退化；被排除目录内的工具结果不受影响（`read_file` 等接收显式路径的工具**不做任何排除**，指定写哪个文件就读哪个文件）。
- N5: 代码规范——按项目语言的标准格式化 / 静态检查 / 测试命令全部通过（本项目为 Python：`ruff format --check .` / `ruff check .`，`pytest` 全绿；遵循 CLAUDE.md）。

## 不做的事

- **解析 `.gitignore`**——不读取、不解释项目的忽略文件（`!` 反选、锚定、`**` 等语义一律不实现），排除规则固定为 F1 的两条。
- **排除名单可配置**——不提供配置文件项、环境变量或工具参数来自定义排除目录集合；名单内置固定。
- **新增"是否包含被排除目录"的入参**——不新增布尔开关；进入被排除目录的唯一通路是 F2 的显式搜索根。
- **修订 ch03 的文档**——ch03 的 spec / plan / task / checklist 保持原样不动，修订记录只存在于本章。
- **修正 glob 的"先截断后排序"顺序**——现有实现是遍历中攒满上限即停、之后才排序，因此返回的是任意 100 条（排序后）。这是既有行为、与本次问题无直接关系，本章不处理。
- **改动结果条数上限**——100 条上限保持原值；本章只保证这 100 条不再被噪声目录占用。
- **改动遍历的其他安全行为**——不改变"不跟随目录软链接"的既有行为，不改变权限沙箱对搜索根的校验方式。
- **其他四个工具**——读文件 / 写文件 / 改文件 / 执行命令接收的是显式目标，不存在遍历范围问题，一律不动。

## 验收标准

- AC1: 默认排除生效——在本仓库跑按模式找文件 `**/*.py`，返回结果中**不含任何** `.venv` 路径，且项目自身文件正常命中。（F1）
- AC2: 三类噪声全覆盖——隐藏目录（`.venv` / `.git` / `.mypy_cache` / `.pytest_cache` / `.ruff_cache` / `.potatocode`）、`__pycache__`、`node_modules` 均不出现在两个工具的默认遍历结果中；被排除目录的**深层子目录**内容同样不出现。（F1）
- AC3: 正常目录不受影响——`src` / `tests` / `docs` / `examples` 等非隐藏、非噪声目录照常参与遍历与匹配。（F1）
- AC4: 逃生口有效——把搜索根显式指向被排除目录（如依赖包目录内）时能搜到结果，不被规则误伤；搜索根指向普通目录时其自身的名字不被拿来判定排除。（F2）
- AC5: 两工具一致——按模式找文件与搜代码内容默认排除行为一致；搜代码内容的文件名过滤参数与排除规则**叠加**生效（如"排除生效 **且** 只搜 `*.txt`"）。（F3）
- AC6: 配额保真——排除噪声后，返回结果条数等于项目自身真实匹配数（未触及上限时），即配额不再被噪声挤占；具体以 `**/*.txt`、`**/*.json` 两个此前被污染最严重的模式验证。（F1）
- AC7: 效率达标——默认范围（排除噪声后 12,670 行）全量搜代码内容在本仓库耗时低于 1 秒；显式搜全量语料低于 5 秒。（N1）
- AC8: 扫描吞吐对齐——同一份全量语料（本仓库 1,148,661 行）下，逐行扫描耗时不超过朴素按行迭代的 1.5 倍（实测改法 0.81s vs 0.81s）；且改法扫描产出的**行号序列与命中集合与改动前逐条一致**（验证：对同一语料用新旧两种扫描实现各跑一遍，断言行数与命中完全相同）。（F4）
- AC9: 超长行语义保持——构造含超长行的文件，仍然：命中阈值范围内的内容、对被截取的行标注未完整搜索、不把整行读入内存（内存不随行长度线性膨胀）。（F4）
- AC10: 接口零变化——两个工具的名称、参数 Schema、只读标记、结果文本格式（路径列表 / `文件:行号:内容` / 截断标注）均与改动前一致；工具定义总数与顺序不变。（N2）
- AC11: 既有回归通过——ch03 的 glob / grep 既有单测全部通过；无匹配、非法正则、单文件读失败跳过、结果截断等既有行为不变。（N3）
- AC12: 不破坏 ch04~ch08——Agent Loop 多轮编排、只读并发、权限沙箱、MCP 工具注册、上下文管理相关测试全部通过；`read_file` 等显式路径工具不受排除规则影响（指定被排除目录内的文件仍能正常读取）。（N4）
- AC13: 代码规范——`ruff format --check .` 通过、`ruff check .` 无告警、`pytest` 全绿。（N5）
